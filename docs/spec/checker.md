# 更新檢查器（Update Checker）

比對 exhentai 上指定作者／團體的最新發布，與本機藏書對照，找出還沒收的書。

原本規劃為獨立專案 `NewUpdate_Checker`，決議併入 FileManager，之後於此維護。

---

## 定位與邊界

| 項目 | 決定 |
|---|---|
| 程式位置 | `app/checker/` 子套件，不散落進既有檔案 |
| 介面 | FileManager 工具列圖示 → PyQt5 面板（摘要）→ 內嵌 Web UI（詳情） |
| 觸發 | **純手動**。按鈕啟動，背景執行緒跑，可隨時中止 |
| 對既有程式的改動 | `file_manager.py` 掛載約 20 行、`.gitignore`、`FileManager.spec`。`authors_db.py` 不動 |

Checker 單向依賴 FileManager（`authors_db`／`paths`／`everything_sdk`／`search_query`／PyQt5），
反向不依賴。移除方式：刪掉 `app/checker/` 並復原 `file_manager.py` 的掛載程式碼。

**性質改變**：FileManager 因此從純本機程式，變成會對外連線並開啟 loopback TCP port 的程式。
這與 [gui_bridge.py](app/gui_bridge.py) 刻意避開 TCP 的設計取向相反，是有意識的取捨——
瀏覽器要連上 Web UI 就必須有 port。port 僅綁 `127.0.0.1`。

## 資料流

```
authors.db 的 427 個實體（有 english_name 者）
  │
  ├─ artist:{english_name} 或 group:{english_name}
  ▼
exhentai.org/tag/... ──► 抓 gid + token（每頁 25 筆，依發布時間新→舊）
  │
  ▼
api.e-hentai.org/api.php (method=gdata) ──► title / title_jpn / posted / tags / category
  │
  ▼
正規化比對 ◄── authors_db.search_terms_for() + Everything 搜出的本機檔名
  │
  ▼
四區塊結果 ──► authors.db 新表 ──► 面板摘要 / Web UI 詳情
```

`title_jpn` 是比對成敗關鍵：本機檔名是日文，格式與 `title_jpn` 幾乎一致。

```
本機：(C77) [40010壱号 (40010試作型)] 美柑はパンツはさくらいろ (To LOVEる -とらぶる-) [中国翻訳].zip
站上：(C77) [40010壱号 (40010試作型)] 美柑はパンツもさくらいろ (To LOVEる -とらぶる-) [英訳]
```

只用站上的英文 `title` 比對會全數落空。

## 掃描規則

**範圍**：全部 427 個有 `english_name` 的實體，支援參數縮小（`--only`／`--top N`）。
缺 `english_name` 的 6 位作者與 3 個團體跳過，並列在報告中提醒補齊，不自動猜測。

**取幾筆**：首次掃描每個 tag 取最新 25 筆建立基準；之後取到「發布時間早於上次掃描時間」為止，
上限 50 筆（2 頁）。翻到上限仍未追上者，標示「此作者可能有遺漏」，不靜默吞掉。

這兩個數字是**預設值，不是寫死的**：「選項 → 更新檢查筆數…」可各自調整，範圍 25–500，
存在 `config.ini` 的 `[Checker]`（見 [settings.md](settings.md) 的 SET-15）。
作者發書快慢差很多，藏書斷了半年再開的人 50 筆根本追不回來，只會每位都標上
「可能有遺漏」——那個標示本來就是在說「上限不夠」，得有地方調。

兩個數字分開設，因為成本不同：首次掃描的筆數**每位作者都要付**（427 位 × 每多一頁
≈ 多跑一輪 25–35 分鐘），回溯上限只有在該作者真的發了那麼多本時才會用到。
合成一個數字會讓「想追回久違的某位作者」直接把首掃時間翻倍。

設定由 `app/checker/limits.py` 讀出，`scan_all` **只讀一次**再往下傳：幾百個實體逐一
去讀同一個檔案，讀到的還是同一份。

首次掃描取滿一頁（25）而非 10 筆，因為那是免費的：tag 頁本來就一次回 25 筆、gdata 的
`API_BATCH` 也是 25，所以無論取 10 還是 25，每個實體都是 2 次請求。語系限縮會吃掉這個
額度（實測約四分之一被排除），額度太小會讓基準只剩個位數。

**去重**：同一本書同時掛 artist 與 group tag 會被查到兩次，以 `gid` 去重。

**聚合**：`gid` 去重擋不住重複上傳與多語版本——實測同一本書可同時有韓譯、西譯、葡譯三筆，
各自是不同 gid，卻全對到同一個本機檔案。因此再依核心標題聚合成「作品」，一部作品一列，
版本收在該列底下。計數也以作品為單位，否則數字會被重複上傳灌水。

**分類**：不過濾。篩選器做在 Web UI，後端寫死規則容易誤殺。

## 比對判定

正規化步驟：去副檔名 → 去事件前綴 `(C77)` → 去社團／作者方括號 → 去作品系列括號
→ 去語言與漢化組後綴 → 餘下核心標題。

三級判定：

| 判定 | 條件 |
|---|---|
| 已有 | 正規化後完全相同 |
| 疑似已有 | 相似度 ≥ 門檻（預設 0.85，可調） |
| 新書 | 無相似項 |

**版本處理**：核心標題相同即算已有，但若站上版本是偏好版本（中譯／無修正）而本機沒有，
單獨列為「版本升級」。

### 語系限縮

**規則**：語言集合為空（＝日文原版）或完全落在 `{japanese, chinese}` 之內才通知，
**只要出現任何一個白名單外的值就排除**，判 `VERDICT_SUPPRESSED`，入庫但不進任何清單。

語言集合是兩個來源的聯集：

| 來源 | 做法 |
|---|---|
| 站上 tags | 讀 `language:` namespace 的值本身（`titles.site_language_markers`） |
| 本機檔名／標題括號 | 14 語言關鍵字比對（`titles.detect_markers`） |

標記集合裡的語言一律帶 `lang:` 前綴，與品質標記（`decensored`、`digital`）分開。
前綴不是裝飾：站上的語言值不受我們控制，`language:ukrainian` 這種沒列進字典的值
也必須認得出「這是一個語言」。

`language:` namespace 裡的 `translated` 與 `rewrite` 忽略——它們伴隨真正的語言 tag
出現，由那個 tag 自己判。其餘沒列到的值（`textless narrative`、`text cleaned`）不在
白名單內，一律排除。

**三個踩過的坑：**

**1. 靠關鍵字字典判站上語言，白名單會變成黑名單。**
`_LANGUAGE_KEYWORDS` 只列得出 14 種語言，站上超過 30 種。`is_wanted_language()` 的
語意是「認不出語言 ⇒ 當日文原版 ⇒ 收」，於是 dutch、czech、ukrainian… 全部從白名單
底下溜過去。改讀 namespace 才是真白名單：沒列到的預設被排除，而不是預設被收。
順帶也擋掉 `female:` / `other:` 裡剛好含語言名稱的 tag 造成的誤判。

**2. 嚴格而非寬鬆（任一命中白名單就收）。**
站上的 language tag 常常沒跟上：日文 tag 掛著沒改、標題卻已經寫明是英譯本。寬鬆規則
會被「japanese 在白名單裡」拖著放行，等於整個聯集白做。

實測 5 位作者最新各 25 本共 103 本，兩種規則**判定完全相同**（各排除 27 本，26%）——
擔心的多語 gallery 誤殺在 tag 頁這個情境下不存在：

| 語言集合 | 本數 | 判定 |
|---|---|---|
| （無） | 53 | 收（日文原版多半根本沒掛 language tag） |
| chinese | 19 | 收 |
| chinese + japanese | 4 | 收 |
| english / korean / spanish | 21 | 排除 |
| vietnamese / french / ukrainian / turkish / text cleaned | 6 | 排除 |

**3. 排除與本機有沒有這本無關。**
早期版本只在「本機已有同名書」時才靜音，理由是沒收過的作品仍該讓使用者知道它存在。
實際用起來不成立：只有韓譯／英譯版存在的書，使用者本來就不會收，通知他只是噪音。
代價要講明白——**只有非中日文版本的書，使用者永遠不會知道它存在**。

本機藏書實測分佈支持這條規則：

| 標記 | 本機檔案數 |
|---|---|
| 中国翻訳 / 漢化 / Chinese | ≥2000（截斷）/ 834 / 291 |
| 無修正 / DL版 | ≥2000（截斷）/ ≥2000（截斷）|
| 英訳 / English | 1 / 8 |

**報告四區塊**：`🆕 新書`、`⬆️ 版本升級`、`❓ 疑似已有`、`✅ 已有`（預設摺疊）。

## 狀態記憶

資料表建在 `authors.db`，但 schema 由 `app/checker/store.py` 自己套用，
因此 **`authors_db.py` 一行都不必改**。新表對舊版 FileManager 是純增加，
舊版開同一個 db 照常運作，只是看不到這些表。

| 資料表 | 內容 |
|---|---|
| `checker_state` | 每個實體的上次掃描時間、分頁基準、截斷與錯誤旗標 |
| `checker_decisions` | 使用者的決定：`ignored`（永不再現）或 `downloaded`（已下載待驗）|
| `checker_findings` | 最近一次的比對結果，供面板與 Web UI 直接讀取 |

### 三條不可違反的規則

**1. `save_findings()` 不可先 DELETE 再插入。**
增量掃描只取回上次之後的新增項目。若先清空該實體的舊資料，使用者還沒處理完的項目
會整批消失——實測第二輪只取回 1 筆，就把前一輪 19 筆待處理的書洗掉了。

**2. 既有判定靠 `refresh_verdicts()` 更新，不靠重掃。**
使用者下載完某本書之後，增量掃描不會再抓到那個 gid（它比分頁基準舊），
沒有這步它會永遠停在「新書」，明明檔案已經在本機了。這步不花網路成本，
只是拿當前的本機檔案清單把舊判定重算一次。

**3. `reconcile_downloads()` 直接查資料庫，不接 `load_findings()` 的輸出。**
`load_findings()` 會濾掉所有已有決定的項目，而待驗中的 gid 正好都在被濾掉的那一批，
接它的輸出會讓「已下載待驗」永遠無法轉正。

### 分頁基準為何存站上時間

`checker_state.last_posted` 存的是站上看到的最新一筆發布時間，不是本機時鐘。
分頁要靠「這筆比上次看到的舊了嗎」決定何時停，兩邊時間必須同源；
本機時鐘與站方時區有時差，拿來當基準會在邊界少抓或多抓幾筆。

## 登入憑證

cookie 放 `runtime_root()/exhentai.txt`（與 `config.ini`、`authors.db` 同待遇），
格式為一行一組 `key=value`，需要 `ipb_member_id`、`ipb_pass_hash`、`igneous`。

**實際路徑**：本機的 `FILEMANAGER_HOME` 指向 `D:\filemanager`（打包後 exe 的所在地），
因此 `runtime_root()` 解析到那裡，cookie 的正解位置是 `D:\filemanager\exhentai.txt`。
那個目錄在 git repo 之外，憑證物理上不可能被 commit。專案目錄內不放副本。

注意同一個原因：真正在用的 `authors.db` 也在 `D:\filemanager`，專案目錄那份是舊的開發副本。

**這個檔案絕不可進版控。** `.gitignore` 已排除 `exhentai.txt` 與 `*.cookies`。

強制規則：

- cookie 值永不寫進 log、例外訊息或 Web UI 頁面
- 找不到 cookie 檔就明確報錯，**不退回匿名請求**（避免以為有登入其實沒有）
- 偵測到 sad panda（cookie 失效）立即停止整輪，提示更新檔案

## 速率控制

站方會擋頻繁請求，全掃 427 個 tag 約 25–35 分鐘。

- 請求間隔 4 秒，隨機抖動 ±1 秒
- 遇 429／503 指數退避
- **連線類錯誤（讀取逾時、連線重置、SSL 錯誤）走同一條退避重試路徑**。
  它們都是 `OSError` 的子類，只接 `urllib.error.URLError` 會漏掉 `read()` 逾時
  拋的 `TimeoutError`——實測跑到第 244／440 位時一次讀取逾時就報銷整輪 20 分鐘
- 連續 3 次失敗即中止整輪並回報
- 中止後已掃部分照常保留，下次接著跑

**中止類錯誤以 `ScanAborted` 表示**（`CookieExpired` 是它的子類），`scan_all` 直接往上拋。
一般的 `CheckerError` 是「這一位失敗、換下一位」；中止類若也走那條路，訊息說
「已中止本輪掃描」，程式卻默默跑完剩下的幾百位，每一位都記上同一個假的失敗。

### 實際請求量

一位作者 = 1 次 tag 頁 + 1 次 gdata（一次 25 筆，站方文件的單次上限）。
440 位一輪約 880 次請求、間隔 4 秒 ≈ **0.25 req/s**，單執行緒、同時只有一個請求在飛。
`app/checker/thumbs.py` 抓 ehgt.org 的縮圖有**自己的節流器**（見下方「下載節流」），
因為那條路徑不是掃描發動的，而是瀏覽器捲到才觸發。

## Web UI

`app/checker/webui.py`。面板雙擊項目或按工具列的「詳細清單」即以系統預設瀏覽器開啟。
伺服器由 `CheckerPanel` 持有，與主視窗同生共死。

四區塊分頁、縮圖牆、標題與作者搜尋、分類篩選器（分類不在後端過濾，寫死規則容易誤殺），
每張卡片可直接標記「已下載」「忽略」或開啟站上頁面。「疑似已有」的卡片會並排顯示
對到的本機檔名——那正是判斷的依據。

### 安全邊界（不可放寬）

| 邊界 | 作法 |
|---|---|
| 不對外開放 | 只綁 `127.0.0.1`，埠號由系統指派（`port 0`，寫死會被佔用而啟動失敗）|
| 存取控制 | 每個請求都要帶對 token，否則 403。token 每次啟動重新產生 |
| 不外洩憑證 | 頁面與 API 永不輸出 cookie 值；**存取紀錄整個關掉**，因為網址帶著 token |
| 不連外部主機 | HTML／CSS／JS 全部內嵌，並以 CSP 把瀏覽器一併鎖住 |

## 縮圖

**下載到本機快取後由 Web UI 供應，不引用 `s.exhentai.org`**。頁面若直接引用站方網址，
瀏覽器會對站方發出幾百個外連請求，很容易被判成盜連而整片破圖；而且瀏覽器沒有登入
cookie，本來就未必拿得到。

視同網際網路暫存檔：可隨時整個刪掉，下次瀏覽自動補回來。上限 512MB，超過時從最久
沒被讀取的開始汰換。已列入 `.gitignore`。頁面用 `loading="lazy"`，只有捲到的卡片才會
觸發下載，開啟頁面不會一次打幾百個請求。

### 卡片順序

卡片由上而下是**書名與後設資料 → 縮圖 → 三顆按鈕**。

按鈕貼著縮圖的下緣，因為判斷「已下載／忽略」看的就是封面——決定與依據要在同一
個視線落點上，中間不隔東西。

**同一橫排的縮圖與按鈕必須切齊在同一高度**，不得因為書名長短而各自浮動——一整排
高低不一的按鈕，眼睛得逐張重新找。作法是把卡片切成三格 subgrid，列高向父格線借：
書名長的那張只會把整排的縮圖與按鈕一起往下推。排距改用卡片自己的 `margin-bottom`，
因為父層的 `row-gap` 會被 subgrid 借走，變成卡片內部三格之間的空隙。

> 按鈕原本排在縮圖**上面**，理由是「圖高度隨原圖比例變動，只有擺最後才不會把下面
> 的東西推歪」。那個理由後來失效了：縮圖改成固定 5:7 的框 ＋ `object-fit:contain`
> 之後每張圖一樣高，推不歪任何東西。

### 卡片外框

卡片外框用**對比色** `--frame`（淺色 `#2f66d0`、深色 `#7aa8dc`），寬度 2px，
不是分隔線用的低對比 `--line`。**兩種配色都要各自定義**——深色沒定義會沿用淺色那組，
深底配深藍框等於沒有框。

卡片**內部**的分隔線（縮圖上緣、按鈕上緣）維持 `--line` 的低對比：內外都用對比色的話，
外框就不再是外框。

> 一整片同色卡片鋪滿畫面時，低對比的邊界會讓相鄰兩張看起來像同一張，
> 按鈕與縮圖分不清屬於誰。實際觀感 **[手動]**，自動測試只擋得住「又被改回 `--line`」。

### 下載節流

縮圖牆是瀏覽器捲到才觸發下載，一次捲動可能同時打出幾十個請求，而
`ThreadingHTTPServer` 每個請求一條執行緒——掃描器那邊 4 秒一次請求，這裡卻毫無節制，
曾是整個程式對站方最不禮貌的地方。

- 下載之間至少間隔 `MIN_INTERVAL`（0.5 秒，2 req/s）。比掃描器的 4 秒短得多是有理由的：
  那邊打的是要動用資料庫的搜尋頁，這裡是靜態圖片 CDN，站上一頁 gallery 本來就會
  一口氣載入四十幾張
- 節流器是**模組層級的單一份**，等待在持鎖時進行——所有執行緒因此排成一列，
  而不是各自睡完再一起衝出去
- **快取命中不排隊**：節流只擋真的要出門的請求
- 收到 429／503 就停手 `COOLDOWN_SECONDS`（60 秒），期間所有下載直接放棄、顯示佔位圖。
  那是站方唯一一次明說「你太快了」，收到之後繼續重試等於把警告當沒看到

### 顯示尺寸

站方給的縮圖是 250×350 左右的直式封面。**不得裁切**：封面正是判斷「這本我有沒有」的
依據，固定高度加 `object-fit:cover` 會把上下切掉一半以上。改成固定 5:7 的框加
`object-fit:contain`——整張都看得到，而且每張圖佔一樣高。缺圖時後端回的是 1×1 佔位
GIF，沒有這個框它會被撐成一個正方形大洞。

卡片寬度由 CSS 變數 `--cw` 控制，工具列可選 小／中／大／特大（260／340／420／560px），
預設大圖。選擇記在瀏覽器 `localStorage`，不進 `config.ini`——那是看的人當下的偏好，
不是這一輪掃描的狀態，也不該在三個進程之間同步。

點縮圖以滿版檢視（`Esc` 或再點一次關閉）。原圖只有 250px 寬，牆上再放大也有限，
要看清楚封面就得有一個佔滿視窗的檢視。[手動] 實際觀感只能開瀏覽器看。

## 面板與主程式整合

`app/checker/panel.py` 提供 `CheckerPanel`（摘要）與 `ScanWorker`（背景掃描執行緒）。

進入點：中間檔案面板工具列上的書本＋放大鏡圖示，或「檢視 → 顯示更新檢查器」
（Ctrl+Shift+U）。面板預設收起——它只有在剛掃描完才有東西可看，常駐佔寬度不划算。

面板放在 `main_splitter` **最右側**：它是「看結果」的地方，與左側「選作者」的動線
相反，擺同一邊會互相搶寬度。

### 執行紀錄區

清單下方以垂直 splitter 掛一塊紀錄區：進度條（`%v/%m %p%` ＋ 目前作者名）、
已耗時與預估剩餘、逐項紀錄。理由是一輪要跑 25–35 分鐘，狀態列只留得住最後一行，
看不出跑到哪、哪幾位失敗、還要多久。

每位作者掃完記一行（`★ 🆕 2、⬆️ 1（排除 6）`／`── 無更新（排除 3）`／`⚠ 失敗：…`／
`── 略過：沒有填英文名稱`），
資料來自 `scanner.scan_all(on_result=…)`——那個 callback 是為了這塊紀錄而加的，
原本的 `progress` 在實體開始前呼叫，只知道正在跑誰、不知道跑出了什麼。

排除數逐位顯示而不是只給總數，是因為**沉默的過濾器很危險**：語系限縮若壞掉
（站方改了 tag 格式），症狀是每位作者都「無更新」，看不出原因。有「排除 25、新書 0」
這種行才分得出是過濾器出事，還是真的沒新書。

`QPlainTextEdit.setMaximumBlockCount(2000)` 設上限，跑幾百位作者不會累積吃記憶體。
預估剩餘用已完成筆數的平均速度外推。中途停止時進度條停在半途不歸零，那是真的做到哪。

字型跟隨主視窗的 Ctrl+= / Ctrl+-：`CheckerPanel.apply_font_size()` 由
`FileManager._apply_font_size()` 呼叫，與 `AuthorsPanel` 同一條路徑。子元件必須逐一
重設——計數列比內文大一級、紀錄區用等寬且小一級，設過字型的元件就不再從父層繼承。
紀錄區的下限壓在 8pt，否則主視窗縮到 6pt 時紀錄小到看不見。工具列圖示不跟著縮放，
與中間檔案面板的工具列保持同一尺寸。

### 版面狀態的保存

`config.ini` 的 `[Layout]` 記四個鍵：

| 鍵 | 內容 |
| --- | --- |
| `checker_panel_visible` | 面板是否顯示（預設 false） |
| `checker_panel_width` | 面板寬度；隱藏時 `sizes()[2]` 為 0，沿用先前記住的值 |
| `checker_split_sizes` | 清單／紀錄的分隔位置 |
| `checker_col_widths` | 清單三欄的欄寬 |

前兩個由主視窗管（`_apply_main_splitter_sizes()` 那條路徑），後兩個是面板內部的事，
封裝在 `CheckerPanel.layout_state()` / `restore_layout()`——主視窗只負責把字串存進
config，不必知道面板裡有幾格 splitter、幾個欄位。

還原時的兩個守則：`split` 全為 0 代表面板從沒顯示過就被存下來（隱藏 widget 的尺寸
是 0），照套會讓清單與紀錄都變成 0 高，直接跳過；欄寬為 0 同理。紀錄區在 splitter
裡的 stretch factor 是 0，所以視窗高度改變時是清單吸收差額，使用者拉出來的紀錄高度
會原樣留著。

### 重設掃描紀錄

工具列第四個按鈕。清空 `checker_findings` 與 `checker_state`，**保留 `checker_decisions`**
（使用者按過的忽略／已下載是人的決定，不該跟著規則變動被清掉）。清完不自動開始掃描。

需要這個按鈕的理由：判定規則改了之後**舊列救不回來**。`markers` 欄位存的是掃描當下
判出來的結果，當時認不出的語言就是空的，重評也只會再得到「無語言標記＝日文原版」。
要套新規則只能重抓 metadata，而增量掃描以 `last_posted` 為界不會再抓舊項目——
清掉 `checker_state` 才會退回首次掃描。

### 兩條踩過的地雷

**1. `EverythingSDK` 必須在工作執行緒內建立。**
它在建構時會建立一個訊息視窗，而視窗的訊息佇列屬於建立它的執行緒。若沿用主執行緒
的實例，`query()` 會安靜地逾時回傳空清單、不報錯——比對會把整櫃藏書誤判成「本機沒有」，
然後把每一本都列成新書。同樣的坑 `hermes_mcp._get_everything()` 也踩過，註解有記。

**2. `main_splitter.setSizes()` 必須一次給滿三個值。**
`main_splitter` 從兩欄變三欄之後，既有的 `_set_authors_panel_visible()` 還是只傳兩個值，
第三欄會被壓成 0 寬——切換左面板時右面板就無聲消失。已抽成
`_apply_main_splitter_sizes()` 統一計算。

## 實作注意事項

- 純函式（抓取、正規化、比對）與 Qt 完全解耦，方便測試也方便日後搬移
- 所有進入 Qt 事件圈的邊界一律 try/except 收斂，Checker 的錯誤不得拖垮主程式
- 優先使用標準函式庫（`http.server`、`difflib`、`urllib`），減少打包體積與依賴
- 本機檔案對應走 `authors_db.search_terms_for()` + Everything 搜尋，與 `authors-stats`
  同一套機制。注意這代表 **Everything 必須在執行中**，否則比對無法進行
- 併入後在同一進程內，不經 CLI，因此沒有 `gui_not_running` 問題
